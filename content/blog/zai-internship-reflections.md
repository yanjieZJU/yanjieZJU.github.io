在智谱的实习中，我负责了会议纪要生成、待办提取、文档解读、每日早报功能的实现，研究 Skill、Tool、Workflow、上下文管理和评测。这篇复盘想记录过程中曾经反复困扰我的问题：为什么一件看起来很简单的 AI 功能，进入真实业务以后会迅速变复杂？当模型已经“会做”一件事之后，距离真正能被业务使用，还有多远？


## 01 | 会议纪要就是让模型总结一下吗

刚开始接会议纪要的时候，我其实并不觉得它会是一个特别难的问题。

模型本身已经有不错的总结能力。给它一份会议逐字稿，再补充一些输出要求，看起来就已经能生成一篇结构完整、语言流畅的纪要。

真正的问题在开始测试之后出现。

最先暴露出来的是待办提取。

模型提出来的待办总有一种“看起来像待办，但又不太能直接用”的感觉。

比如一句话里有代词，真正的责任人出现在更早的上下文里，这其实是在考模型的指代消解能力；有时领导说“让某某部门后续跟一下”，被指派的人甚至不在参会人里。

再往下追，会遇到一个更根本的问题：到底什么才算待办？

“这个方向后续可以继续研究”算吗？

“原则上同意这个方案”算吗？

“请相关部门进一步讨论”算吗？

如果没有责任人、没有截止时间，只表达了一个方向，它还是待办吗？

这些问题并没有天然的标准答案。

所以那段时间真正有效的工作不是继续加 Prompt，而是先整理出一版判断标准，列出正例、反例和边界情况，再拿给业务方讨论。

## 02 | 政务会议纪要究竟有什么特别

我第一次参与和政府侧的实际需求对齐，将我们按照自己的想法整理出来的规则和生成的案例给客户检查。

在那之前，我对会议纪要的理解还是通用的，就像钉钉、飞书、腾讯会议的智能纪要：准确、完整、语言通顺。

但真实业务里的要求要具体得多。

比如每月的例会，一场会议中按顺序讨论多个议题，每个议题都要形成相对完整的纪要单元——即所谓的“一事一议”结构。

比如会议中部门汇报内容本身往往不是重点。一段很长的项目介绍，最后可能只需要高度概括；真正需要重点保留的，是之后的领导意见、原则性判断和任务部署。

而且生成的纪要甚至需要接近可以直接发文的格式，比如标准的抬头、落款，什么地方应该写“会议指出”，什么地方写“会议强调”……

在这个业务场景中，真正决定产品能否落地或被用户接受并使用的，可能就在于这些非常具体的规则。ChatGPT 将这些规则总结为**业务知识、产品规则和执行约束**。而 Skill 是一种承载它们的形式。

## 03 | 规则写得越完整，效果就越好？

需求明确以后，我需要做的事也越来越明确了：继续往 Skill 里补充规则。格式要求、议题处理方式、会议类型识别、待办标准、领导讲话的写法、会议纪要模板……

然后 Skill 开始越来越长。

某次看 Agent 的执行过程时，我发现一件很“离谱”的事情：

模型在 thinking 里认真地复述：“根据 meeting-minutes 技能要求，我需要先……再……最后……”

看起来它完全阅读并理解了这个 Skill，但接下来执行时，完全没有按 Skill 规定的流程走。这是为什么？

越来越多的约束不仅会占用上下文，也可能互相竞争。Skill 塞得太满以后，不同约束之间可能会相互矛盾；又或者，Skill 的约束和模型训练时习得的知识之间也存在冲突。即便我控制 SKILL.md 主文档在 500 行以内，模型却仍然无法稳定地遵循约定的步骤和规则。

再后来，我看到 Claude 新版本也在强调类似的方向：与其给大模型大量细粒度的禁止项，不如保留关键约束，让模型利用上下文和判断力完成任务。

所以在写 Skill 的时候，哪些应当放在主文档、哪些放在 Reference 里、哪些通过代码执行、甚至哪些规则并不需要放在 Skill 里，都需要仔细地斟酌。

## 04 | 32K 的上下文窗口放不下逐字稿

一场几个小时的会议，加上材料、Skill、历史上下文，很容易超过我们当时设置的 32K 窗口。

一种很自然的想法是，让 Agent 自己分段读取材料，或者把不同部分交给 Subagent 处理。

开始内部更偏好这种模式。但真正跑起来之后，Langfuse 中的 Agent 执行轨迹显示，read_file 经常发生在 load_skill 之前。模型很自然地想“我先看看这个文档”，于是把逐字稿整份读进来了。

这时候我开始寻找代替 subagent 的方法，找到了 Map-Reduce 长文本纪要处理方法。
我想用 Workflow 的方式，让每次模型调用时的上下文内容（固定长度的 chunk，确定的 system prompt，或是针对不同类型会议的特定模板）和结构（头部放规则，中间放历史，末尾拼接新的逐字稿）更可控。

我还对这个方法做了进一步的“改动”：在那篇参考文章中，Map 阶段直接做了摘要，Reduce 阶段用来整合。政务会议里，领导部署本身几乎每句话都是重要事实，如果 Map 阶段过早摘要，很容易把完整的逻辑链拆成碎片。因此我做了一个更保守的划分：
```
Map 负责高召回地保留事实（以及待办），不负责公文写作；Reduce 再负责系统整合和风格化。
```

## 05 | 没有标准答案，要怎么评估？

会议纪要本身没有“标准答案”。按照以往的经验，这一步应该是找到真实用户去审查、打分——可惜我们没有这个条件。

为了找到目前工作流存在的问题，我采用了之前看过的一篇文章—— RubricHub 的评测标准构建方法。这里要承认，是因为我自己都难以规定“什么样的纪要是好的”，所以我寻求模型的帮助（提示词已开源）。它通过对比用户提供的真实纪要和我们生成的效果，找到生成纪要中存在的“失败模式”。

相比于“优秀的纪要应该是什么样的”，我用它来定义“哪些失败是一定不能发生的”：
- 哪些情况绝对不能被提取为待办
- 什么格式不应该出现
- 是否存在事实性错误
- ……

做到这里，我越来越觉得：**评测不只是产品做完以后的验收工具，它本身也是需求定义的一部分。** 为了设计一套评测标准，我们还是要回到最初的需求定义——什么是必须正确的？什么是偏好？什么错误会直接导致结果失去价值？

## 06 | 这到底算不算一段产品经历

实习做到后面，我产生过这样的疑问。

实话说，这不是一个从用户洞察、需求发现、交互设计到上线验证的完整产品闭环。我的工作重心并不在用户增长、完整交互设计或上线后的数据验证，而更多集中在另一段链路：

```
如何把一个模糊的业务需求，逐渐转化成一套可以执行、可以约束、也可以评估的 Agent 能力。
```

ChatGPT 给了我回答：业务标准需要被定义，模型的自由度需要被约束，复杂任务需要被拆解，失败需要被识别，用户需要在合适的时候拿回控制权，而最终我们还必须回答“到底怎样才算做得好” —— 这是将一个看起来已经会做事的大模型变成一个可以被真实业务依赖的产品能力必然经历的过程。

```
把模型能力变成产品能力，本身就是产品设计的一部分。
```
