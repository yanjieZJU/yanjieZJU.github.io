Rubric 是一组自然语言形式的评价标准，每个标准对应一个具体、可评估的质量维度。一个 rubric set 可以由若干个 rubric item 组成，每个 item 包含自然语言描述和重要性权重；对于输入任务和模型输出，judge model 逐项给出分数，再通过平均、加权求和或隐式聚合得到整体评价。

```card
本学习笔记基于中国人民大学高瓴人工智能学院发表的文章[《The Rules of the Game: A Survey of Rubrics for Large Language Models》](https://github.com/RUC-NLPIR/Rubrics_Survey)
```



## Background / 背景

早期的LLM主要应用于那些目标较为明确且输入输出格式相对标准化的任务，例如问题回答、指令遵循、代码补全等；随着LLM能力的快速发展，它们能够处理更加复杂且开放性更高的任务，包括长篇报告生成、专业分析、软件工程、科学发现等。在这些复杂的任务中，并不存在明确的正确答案，响应质量也无法仅通过精确匹配、执行成功或二元正确性等标准来可靠评估。

因此，需要一个结构化且明确的评估标准，能够明确回应应满足的要求。

## Method / 构建方法

### Rubric 的构建维度
- 输入上下文
  - 仅查询：仅基于查询请求和任务描述来制定
  - 查询+答案 / 查询+证据：基于高质量的答案或支持性证据来制定标准
  - 查询+偏好对：通过对比高质量和低质量的回答得出评分标准，从而突出具有区分性的评估维度
  - 训练中的动态生成：模型在训练过程中，根据实际生成回答的质量好坏，动态地推导、更新这些标准
- 输出形式
  - 二元原子评分：每个标准只有“是/否”两种判断
  - 层次化评分：宏观的维度被分解为更细的子维度
  - 正面和负面评分：正向rubric描述高质量回复应该满足的特征，负向rubric描述典型的失败模式
  - 以事实为评分标准的评分：从证据材料中抽取原子级信息单元作为rubric，每条标准都指向一个可以明确判定“有/没有”的事实
  - 与查询无关的通用评分：先为大量个别查询生成验证过的 instance-specific rubric，然后对这些标准做聚类和蒸馏，压缩成跨实例共享的质量维度
- 质量要求
  - 区分性：能够准确区分高质量和低质量的回答
  - 覆盖性：必须涵盖任务中所有重要的评估维度
  - 原子性和可验证性：每个标准都应有足够的细粒度，以便能够明确评估
  - 一致性：评分标准的方向应与人们真实的质量偏好保持一致
  - 冗余性和相关性：避免重叠的标准导致评分重复或增加不必要的干扰
  - 动态鲁棒性：在评估策略不断演变的情况下仍然有效

### 构建方式
![method](blog/rubric_construct_method.png)

1. 直接生成：给定任务指令、候选答案或参考证据，强大的 LLM 可以一次性生成一组评价标准。
2. 对比生成：相比只看一个答案，对比生成会输入偏好对，例如一个高质量回答和一个低质量回答，让模型总结二者差异，从而提取更有判别力的标准。
3. 迭代优化：不把 Rubrics 构造当成一次生成任务，而是引入迭代地验证、分解、压缩等流程。例如检测某个标准是否能稳定区分偏好对，递归拆分过粗的标准，最终得到更原子、更紧凑的 rubric set。
   1. 四种基本错误模式：覆盖不足、维度混淆、方向不一致、标准间存在冗余
   2. 一些解决思路：
      ① 对适用于特定实例的评分标准进行聚类处理，然后将这些标准提炼成可重复使用的“主题-提示”；\
      ② 相关性加权过滤；\
      ③ 分析推理失败的情况来归纳错误类型（避免从积极维度构建导致的冗余）
4. 在线与共同演化：对于强化学习和 Agent 任务来说，静态 Rubrics 可能很快过时。因此，部分工作尝试让 Rubrics 随着模型的训练而更新，将新出现的错误行为纳入评价标准，使 Rubrics 与模型训练过程共同演化。

### 评估方法
1. 失败模式分类法
   1. 把rubric的结构缺陷归入三类：reliability（可靠性，比如主观性太强导致不同评判者打分不一致）、content validity（内容效度，比如标准缺乏原子性、遗漏关键维度）、consequential validity（后果效度，比如标准引导模型走向错误优化方向）。
   2. 对rubric做逐条审计，判断每条标准落入哪种失败模式，属于定性而非定量的诊断工具。
2. 偏好对验证法
   1. 生成候选rubric后，拿它在留出的偏好数据对上测试，检查该rubric的打分是否系统性地偏向被选择的回复而非被拒绝的回复。未通过阈值的rubric送回生成器修改，循环往复直到达标
   2. Generate-verify-revise 闭环
3. Rubric-BLEU 与下游判别力测试
   1. 内在层面：用文本相似度指标，衡量自动生成的rubric与专家撰写标准之间的语义对齐程度
   2. 外在层面：把rubric交给评判模型，看它在区分高质量和低质量回复的偏好任务上准确率是否提升

### RubricHub：一种完全自动化的“从粗到细”的评分标准生成框架
```card
1. 采用以用户反馈为依据、以原则为导向的策略来制定候选评分标准，从而确保这些标准与用户的查询意图保持一致。
2. 整合来自不同模型的多种观点，以确保评分标准的全面性，同时避免单一来源带来的偏见
3. 引入“难度渐进机制”提升评分标准的区分度。该机制不会停留在一般的评分标准上，而是会不断优化评分标准，以捕捉那些具有特殊意义的回答的细微差别。
```
**Stage 1：让生成器以参考响应（而非仅从查询）为依据来生成内容**

理由：仅根据查询来生成评分标准，往往会导致评分标准的合理性缺失——也就是说，所制定的标准会变得过于笼统、不切实际，或者与实际任务要求脱节

做法：让生成器以参考响应为依据来生成内容；使用元原则约束生成器行为

元原则：
  - 一致性与匹配性
  - 结构与范围
  - 清晰度与质量
  - 推理性与可评估性

![dimension](blog/rubric_dimension.png)

**Stage 2：多模型聚合**

理由：单一模型生成的评估标准本身存在视角偏差。各个模型往往都有其固有的盲点与主观偏好，导致评估标准的局限性。

做法：利用不同的模型（如 GPT-5.1、Gemini 3 Pro Preview）来生成多个候选结果，形成统一的候选集；然后通过特定的聚合机制 ，将这些候选结果整合为一个简洁的最终结果（消除重复、解决冲突）。


**Stage3：难度提升**

理由：基础评分标准通常能够确保答案的基本正确性，但往往无法准确区分那些“优秀”和“卓越”的回答。这一局限性会导致评分结果过于平均，使得顶级模型的优化过程缺乏有效的指导。

做法：
1. 从最初的候选答案中挑选出一对高质量的标准答案
2. 运用特定的增强提示来分析这个答案，提取出超出基线回答的关键信息

**应用**

构建RubricHub数据集，包含科学领域、指令遵循领域、写作领域、医学领域和聊天领域的110,000对“问题-评分标准”组合。

在两种后训练的应用场景中使用了这些评估标准：RuFT 用于为监督式微调任务挑选高质量的数据；RuRL 则将评估得分作为奖励机制来使用。

- RuFT：对每个“问题-评分标准”组合，用多个模型生成K个候选回复，每个回复按Rubric打分，将分数归一化，设定阈值τ=0.6，低于阈值的全部丢弃，取剩余中最高分的那个作为训练样本 --> 然后用标准SFT训练。
- RuRL：用 rubric 分数作为 RL 的奖励信号。每条评分标准由打分器打一个二值分数（0 或 1），打分器分两种：语义类标准用 LLM 评判，可验证类标准（格式、字数等）用规则程序判定。最终奖励是所有标准分数的加权归一化求和。

**最佳实践**

1. 准备查询语料。论文从各领域的开源数据集中收集了约 110K 条 query，经过长度异常和格式错误的清洗。你需要收集你领域中具有代表性的 query 集合，规模取决于你的需求。
2. 获取参考回复。Stage 1 要求 response grounding——用一个高质量回复来锚定标准生成，防止 rubric drift（标准变得空泛或与实际任务脱节）。你可以用强模型生成，或者用你领域的专家回复。
3. 定义 meta-principles。论文用了四类元原则（Table 4）：Consistency & Alignment、Structure & Scope、Clarity & Quality、Reasoning & Evaluability。这些原则本身是通用的，但你可能需要加入领域特有的要求。比如医学领域可能需要强调"Safety and Professional Responsibility"，设计领域可能需要加入"视觉一致性"或"用户体验合规性"的元原则。
4. 执行三阶段 pipeline。用你的 query + 参考回复 + meta-principles 跑 Stage 1 生成候选标准；用多个模型做 Stage 2 聚合去重；用你领域中高质量回复对做 Stage 3 难度演化，提取区分"好"和"极好"的细粒度标准。
5. 选择 grader。论文测试了不同规模的 grader（Figure 7），发现 30B 以上模型与人类的一致性趋于饱和（Cohen's Kappa 0.74-0.80），但 7B 模型不够用（κ=0.58）。你需要根据你领域的专业性选一个足够强的 grader，并在小规模数据上验证人机一致性。

## Application / 应用
### 用于模型训练
1. 用于模型训练（RL）
   1. 标准做法：给定输入和模型生成的回答，judge model按rubrics逐项打分，将分数聚合成一个奖励，用于PPO、GRPO等强化学习算法
   2. 其他做法：将rubrics作为生成过程中的指导，模型根据rubric规划回答，或把未满足的rubric转化成反馈指导下一轮改写
2. 用于奖励模型训练
   1. 提升奖励模型的可解释性
   2. 提供更细粒度的 reward model 训练信号
   3. 用于构造更高质量的训练数据

### 用于评测
- 内容事实性：输出中的陈述是否有据可查、是否准确。
- 安全审计：即使事实正确，输出是否包含有害、违规、高风险内容。论文强调这是事实性的“对立面”：事实性确保正确信息的存在，安全审计确保有害内容的缺席。
- 专业呈现与结构连贯：组织是否清晰、格式是否符合场景规范、语气是否合适。
- 实用性与可操作性：输出是否解决了用户的实际问题，而不只是“看起来正确”。
- 推理能力：区分过程质量和结果质量。MathCheck 把推理评估拆成任务理解、中间步骤有效性、最终答案正确性三层。（只看最终答案对不对，会掩盖推理路径上的错误）
- Agent 能力：维度包括 planning（规划）、memory（记忆）、grounding（落地执行）、multi-turn execution quality（多轮交互质量）。TRAJECT-Bench 更细化到工具选择正确性、参数有效性、依赖顺序约束。论文反复强调的一点是：最终成功可以掩盖过程失败，所以 agent rubric 必须保留中间诊断信号。

## Case / 案例
### HealthBench（医学问答）——专家标注的安全导向 rubric
HealthBench 的 rubric 由执业医师手工撰写，用于评估模型在医学对话中的表现。它的核心设计特征是引入了显式的负向 rubric：不仅检查模型“说对了什么”，还检查模型“漏掉了什么危险信号”——比如是否遗漏了关键的用药安全警告、是否给出了危险的分诊建议、是否编造了不存在的临床证据。

采用逐条标准评估的方式，每个对话配有多项由医生撰写的rubrics，每条标准都有一个预设的分值权重，正向指标赋予1至10分不等，负向指标则赋予−10至−1分。（整个HealthBench数据集共有48,562 条不同的评价标准）

这里体现的构建思路是：在高风险领域，正向标准（“回答应准确”）远远不够，你必须**穷举典型失败模式并单独设立扣分项**。论文暗示的一个问题是，这种专家标注方式成本极高，而且不同临床流派的医生可能对同一个问题给出合理但不同的判断——单一专家团队撰写的 rubric 可能编码了一个合法但片面的视角。

### MoReBench（道德推理）——没有唯一正确答案时怎么设 rubric
MoReBench面对的问题是道德困境往往没有客观正确的答案。它的解决方案是把 rubric 的评估重心从“结论是否正确”转移到“推理过程是否完备”。具体维度包括：道德因素识别（是否识别出了相关的道德考量）、过程清晰度、逻辑一致性、结果的可操作性（给那些提供清晰可行建议的回答加分，惩罚那些只做抽象哲学讨论却不给出行动路径的回答）。

每份 Rubric 都会由另一位专家进行评审，评审者可以添加、编辑或删除标准。最终，一个场景包含 20 到 49 条不同的标准。在这个集合中可能同时包含支持“行动A/行动B/都不支持”的理由。然后设计了一个实验来验证rubric的鲁棒性：请两组人类专家，针对同一个道德困境，写出结论完全相反的高质量推理过程，使用 MoReBENCH 的 Rubric 对这两组结论相反、但质量都很高的推理进行评分，发现 “两组得分没有统计学上的显著差异”。

这个例子体现的思路是：**未来的 rubric 评估需要从“单一标准”假设走向多元视角 rubric——评估回答在某个理论框架内是否自洽，而不是强制所有回答排进同一个偏好序列。**

### AdvancedIF（复杂指令遵循）——反作弊设计
AdvancedIF（He et al., 2025b）通过设计对抗机制来惩罚为了完成指令而进行的作弊行为：
- 元认知欺骗：模型不直接回答问题，而是输出“所有指令都已遵循”或“这是一个完美响应”之类的自评性废话，试图“说服”评判模型给它高分。
- 输出不完整：模型生成了非常长但被截断的回答，利用评判模型可能无法处理长文本的漏洞，来规避对后续内容的检查。

作者增加了两条专门的“防作弊”Rubric，并加入到每个训练样本中，作为给评判模型的额外指令：
1. 防废话/自评：模型是否提供了一个干净的（clean）回答，没有出现诡异的自评或废话？
2. 防截断：模型是否提供了完整的回答，最后的句子没有被截断？

这个例子说明 rubric 设计不仅要考虑“评什么”，还要**预判模型可能的博弈行为并设计对抗机制**。
